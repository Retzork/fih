# P2.15 - the resource system: `properties\resources.xml` and the `ResourceManager`

Status: COMPLETE (2026-11-02); evidence EV-0150..EV-0154, questions Q-0032/Q-0033.
Scope: how the shipped manifest is parsed, how ids and paths resolve, how an `<Image>` entry becomes a
sliced/animated sprite with an alpha mask, how `<Sound>`/`<Font>` entries load, how the three groups
drive startup, and what the typed lookups hand back. Ends with the implementation spec for P4.

Prior work this builds on: P3.1 (manifest inventory, EV-0024/EV-0025), P3.2 (geometry, mask files,
EV-0026/EV-0027), P3.5 (committed `SpriteFrames`, `tools/godot/gen_spriteframes.gd`), P2.14 (the
`SoundRes` load path and the 65 `SOUND_*` ids, EV-0149), P2.1 (the 10 ms logic tick).

## 1. What the manifest is

`properties\resources.xml` is a hand-written XML file - *not* XML the way a parser expects it: it
uses unquoted attribute values (`cols=3`) and bare boolean attributes (`ddsurface`), which is why
P3.1 had to parse it loosely (EV-0024). The engine ships its own tiny XML tokenizer for it
(`Sexy::XMLParser`, allocated as a 124-byte object at `manager+0x34`).

Sizes, all re-derived this pass with `tools/p2.15-groups.js` (see
`docs/analysis/inputs/p2.15-groups.txt`):

| element | count | note |
| --- | --- | --- |
| `<ResourceManifest>` | 1 | the only root the loader accepts |
| `<Resources id=...>` | 3 | `Init`, `Register`, `LoadingThread` |
| `<SetDefaults ...>` | 7 | 3 in `Init`, 2 in `Register`, 2 in `LoadingThread` |
| `<Image>` | 246 | 11 + 3 + 232 across the groups |
| `<Font>` | 15 | 2 + 13 + 0 |
| `<Sound>` | 65 | 1 + 0 + 64 |

326 resource ids in total. The group handlers in the binary reference **exactly** 326 ids and the
partition is exact: `Init` 14, `Register` 16, `LoadingThread` 296 - no id appears in two groups and
none is missing (`p2.15-groups.txt`, cross-check section).

## 2. The three groups and the boot order

`<Resources id="X">` bodies are handed to `FUN_0050FF10(name)`, which is a straight
`strncmp`-chain over three names - `Init`, `LoadingThread`, `Register` - and returns 0 for anything
else (no error, the section is simply ignored). Each handler walks the group element by element,
fetches every resource by its full id through the manager's own vtable, and stores the resulting
pointer in a dedicated global.

| group | handler | resources | when |
| --- | --- | --- | --- |
| `Init` | `FUN_00506EA0` | 14 | synchronously, before the first frame |
| `Register` | `FUN_0050E190` | 16 | synchronously, right after `Init` |
| `LoadingThread` | `FUN_005073E0` | 296 | on the background loading thread, behind the loader bar |

Both synchronous handlers set `DAT_005E8F17 = 1` as their first statement - a "boot resources are
resident" flag that later code checks before touching the globals.

**`Init` (14)** - the earliest usable set, everything the loader screen itself needs:

- fonts `FONT_JUNGLEFEVER10OUTLINE`, `FONT_JUNGLEFEVER17OUTLINE`;
- images `IMAGE_BLANK`, `IMAGE_CURSOR_{POINTER,HAND,DRAGGING,TEXT}`, `IMAGE_TITLEPAGE`,
  `IMAGE_TITLEPAGEMASK`, `IMAGE_LOADERBAR`, `IMAGE_LOADERBAROVER`, `IMAGE_LOADERBARLOADING`,
  `IMAGE_LOADERPLAY`;
- sound `SOUND_BUTTONCLICK`.

**`Register` (16)** - widget skins and the UI font set: 13 fonts (`FONT_LIDDIE{12,15,18}`,
`FONT_JUNGLEFEVER{12,15}OUTLINE`, `FONT_BLAMBOTPRO{8,15}`, `FONT_TINY`, `FONT_TINYBOLD`,
`FONT_CONTINUUMBOLD{12,12OUTLINE,14,14OUTLINE}`) plus `IMAGE_DIALOG`, `IMAGE_DIALOGBUTTON`,
`IMAGE_EDITBOX`. `FONT_JUNGLEFEVER10/17OUTLINE` and these 13 are the complete 15-font set - the game
never loads a font outside the manifest.

**`LoadingThread` (296)** - the bulk art and all in-game audio: **232 images and 64 sounds**. The
handler's shape matters for P4 because it is the one place the whole in-game asset list is
enumerated: 296 calls of the form "push id string, `GetImage`/`GetSound`, store to global". The
full list is `docs/analysis/inputs/p2.15-loadingthread-ids.txt`; the 16 `Register` ids are in
`p2.15-register-ids.txt`, the 14 `Init` ids are read straight out of `FUN_00506EA0`.

Those three counts are the manifest counts minus what the other groups already covered
(`246 = 11 + 3 + 232`, `15 = 2 + 13`, `65 = 1 + 0 + 64`), which is why the arithmetic closes
three ways: manifest elements, group-handler ids, and the per-group source split.

## 3. The parsing pipeline

```
FUN_00418780(path)                       ResourceManager::LoadManifest
  parser = new XMLParser()               manager+0x34, 0x7C bytes
  if (!parser->Open(path))               throw "Resource file not found: <path>"
  loop
    token = parser->Next()
    token.kind == StartElement
      name != "ResourceManifest"  ->    throw "Expecting ResourceManifest tag"
      else FUN_00418420()                parse the manifest body, then unwind
    token.kind == EndElement     ->      done
    otherwise                    ->      throw "Element Not Expected '<name>'"

FUN_00418420()                           <ResourceManifest> body
  for each child element
    name == "Resources"
      id = <element>.attr("id")           fatal "No id specified." when absent
      manager+0x30 = id
      vtable slot 5(id)                 -> FUN_0050FF10         -- group dispatch, §2
    otherwise                  ->  throw "Invalid Section '<name>'"
  at document end: frees the parser (manager+0x34) and nulls it

FUN_00417F10()                           a <Resources> body
  vtable +0x08 -> "Image"        image entry parser   FUN_004166C0
  vtable +0x04 -> "Sound"        sound entry parser
  vtable +0x0C -> "Font"         font  entry parser
  vtable +0x10 -> "SetDefaults"  FUN_00417CA0
  otherwise                  ->  throw "Invalid Section '<name>'"
  unknown *element* inside an entry -> throw "Unexpected element found."
```

Everything is fatal: the whole manifest load aborts on the first malformed tag, unknown section or
unexpected child. There is no recovery, no partial load and no logging - each site builds the
message above (`FUN_0041D8B0`) and then leaves through the framework's rethrow helper
`FUN_00415BA0`, which is why the normal continue/cleanup code that follows is unreachable.
P4 should be *stricter in the tooling and laxer at runtime*: the same manifest is already validated
by `tools/parse-resources.ps1`, and the Godot side should never fail to boot because of one bad
entry.

## 4. Ids, paths and extension probing

`<SetDefaults>` supplies two inherited strings, both replaced wholesale by each occurrence:

- `path` - the directory prepended to every subsequent entry's `path` attribute,
- `idprefix` - the prefix prepended to every subsequent entry's `id` attribute.

So `SetDefaults path="images" idprefix="IMAGE_"` followed by `<Image id="BLANK" path="blank"/>`
yields id `IMAGE_BLANK` and file `images\blank`. `Init` switches defaults three times (images ->
data -> sounds), `Register` twice (data -> images), `LoadingThread` twice (images -> sounds); see the
per-group chains in `p2.15-groups.txt`.

Actual file lookup is `FUN_0049FED0(name, lookForAlpha)` and works like this:

1. split `name` at the **last** `.` that comes after the last `\` or `/`, giving base and extension;
2. if an extension is present, only that decoder is tried; if there is no extension, all six
   decoders are probed **in this fixed order**:
   `.tga` (`FUN_0049BFD0`), `.jpg` (`FUN_0049F800`), `.png` (`FUN_0049BE40`),
   `.gif` (`FUN_0049C160`), `.j2k` (`FUN_0049FB10`), `.jp2` (`FUN_0049FB10`);
3. a failed load is reported by the caller as `"Failed to load image: <name>"`.

The probe order is why the install's mixed extensions (`.gif` sprites, `.jpg` backgrounds) all work
from extensionless manifest paths, and why `parse-resources.ps1` had to mimic exactly this order
(it also handles Windows case-insensitivity, which the engine gets for free).

Sound and font paths work the same way but go through their own loaders: sounds accept the audio
extensions (`.ogg`, `.au` - 50/15 in the shipped set) and fonts are `.txt` bitmap-font descriptors.

## 5. `<Image>` entries

### 5.1 The parser

`FUN_004166C0` allocates a 0x110-byte `Sexy::Image`/`MemoryImage`, asks the entry to fill it, then
reads the attributes one by one. The order and the exact attribute names (all resolved from
`.rdata` this pass) are:

| attribute | field | meaning |
| --- | --- | --- |
| `path` | - | file stem, joined with the current default `path` |
| `nopal` | `+0xCD` | bare; image is not palettised |
| `a4r4g4b4` | `+0xCE` | bare; 16-bit texture format |
| `ddsurface` | `+0xD0` | bare; keep as a DirectDraw surface (the six `AQUARIUM*`) |
| `nobits` (+`nobits2d`/`nobits3d`) | `+0xD1` | bare; skip the CPU-side pixel copy |
| `a8r8g8b8` | `+0xCF` | bare; 32-bit texture format |
| `minsubdivide` | `+0xD2` | bare; texture-manager subdivision hint |
| `noalpha` | `+0xCC` | bare; declared opaque, do not build an alpha channel |
| `alphaimage` | string | explicit mask image, see §5.3 |
| `alphacolor` | `+0xDC` (default `0xFFFFFF`) | hex colour, `sscanf("%x")` |
| `variant` | string | free-form tag; cleared, never used by the loader |
| `alphagrid` | string | explicit mask *cell*, see §5.3 |
| `rows` | `+0xD4` (default 1) | grid rows, `atol` |
| `cols` | `+0xD8` (default 1) | grid columns, `atol` |
| `anim` | `+0xE0` | `none`=0, `once`=1, `pingpong`=2, `loop`=3 |
| `framedelay` | `+0xE4` | per-frame delay, `atol` |
| `begindelay` | builder arg | delay before the first frame |
| `enddelay` | builder arg | delay after the last frame |
| `perframedelay` | int list | comma-separated per-frame override |
| `framemap` | int list | comma-separated frame order |

An unrecognised `anim` value raises `"Invalid animation type."` and aborts the manifest load - the
`return 0` that follows the message in the decompile is unreachable cleanup, since the message
helper rethrows before returning. `framemap`/`perframedelay` are parsed with the same comma-list
helper the options code uses; a list shorter or longer than the frame count is not rejected at
parse time (the builder normalises it, §5.2).

### 5.2 Grids and animation

- A grid is sliced into `cols * rows` cells; absent `rows`/`cols` mean 1. Every one of the 246
  images' effective grids divides exactly (P3.2).
- Frame *index* order is row-major - `col = i % cols`, `row = i / cols` - which is what
  `gen_spriteframes.gd` already does, and what `framemap` indexes into.
- `anim` values map onto the classic four behaviours, and the shipped manifest uses three of them:
  **56 `loop`**, **8 `pingpong`** (`WAVE`, `WAVESIDE`, `NIKO`, `VERT`, `WALTER` and their three
  `SCL_*` silhouettes), **2 `once`** (`MERYLBLINK`, `MERYLTAIL`); no entry uses `none` because
  omitting the attribute already means "not animated".
- 66 entries are animated; 65 of them declare `framedelay`, and **every** value in the shipped
  manifest is `2` or `4`. With the 10 ms logic tick from P2.1 that is 20 ms and 40 ms per frame
  (50 and 25 fps). The one exception is `MERYLBLINK`, which declares only `perframedelay` - the
  builder clamps its missing default to 1 tick (Q-0032 records the residual: the countdown itself
  lives in the animation update, which belongs to P2.2's object model).
- 111 entries declare `cols`, 52 declare `rows`; 66 grid-declaring entries are animated and **48 are
  not** (effects strips, `IMAGE_MISSILE` 16x1, `IMAGE_BUBBULATOR` 1x20, ...). Those are sliced and
  indexed by gameplay code with explicit frame numbers - P4 needs the cell count even when `anim`
  is absent, which is why `extraction.json` keeps `cols`/`rows`/`cellW`/`cellH` for all of them.
- `framemap` is used twice: `MERYLBLINK` `0,1,2,1,0,-1` and `MERYLTAIL` `7,6,5,4,3,2,1,0` (a full
  reversal). The `-1` in the blink map is the open item from P3.5 (EV-0027) - see §5.4.
- `perframedelay` is used once, on `MERYLBLINK`, and has exactly as many entries as `framemap`
  (`3,2,3,1,1,1`), i.e. the two lists are parallel: a per-frame override of `framedelay` for the
  mapped sequence.
- `begindelay` is used three times (`MERYLTAIL` 3, `WAVESIDE` 6, `WAVE` 6) - a dwell before the
  animation starts, which is what makes the tail and the wave read as "slow, then moving".

**The animation is built once, at load** (`FUN_004575E0(data, beginDelay, endDelay)`), and that
builder settles several things the manifest leaves implicit:

- the anim record is `{type, defaultDelay, frameCount, perFrameDelays, frameMap, totalDuration}`;
  `frameCount` and `defaultDelay` are clamped to at least 1;
- **`pingpong` is expanded, not interpreted**: when `type == 2` and there are N > 1 frames, the
  builder writes the explicit sequence `0,1,…,N-1,N-2,…,1` into the frame map. Godot's `pingpong`
  animation mode is equivalent *except* at the turn, so P4 can either expand it the same way (exact)
  or use the mode (one frame shorter at the ends);
- if a `framemap` was supplied it **replaces the sequence** and the frame count becomes the map's
  length - so `MERYLTAIL` plays 8 steps of a `cols=8` sheet in reverse, and `MERYLBLINK` plays 6
  steps of a 3-cell sheet;
- `perframedelay` entries below 1 are replaced by `framedelay`, so a partial list is legal and the
  omitted behaviour is "default delay" - that is why `MERYLBLINK`'s six values line up with its six
  map entries;
- `totalDuration` is precomputed as `frameCount * framedelay` when there are no per-frame delays,
  otherwise as the sum of the per-frame list. This is the strongest single argument that delays are
  **integer ticks** and not seconds: an animation's length is an integer sum used for the loop
  period (Q-0032b keeps the exact unit open, since the tick length itself comes from P2.1).

Total honestly-declared animated art is 66 of 246 images; the remaining sheets are manual frame
tables, so P4's sprite layer needs both `AnimatedSprite2D`-style playback and direct cell indexing.

### 5.3 Alpha masks - the two-file model

The install ships every base image as an opaque GIF/JPG; transparency comes from a **second file**.
Two mechanisms exist, and they are not the same:

1. **Implicit companion** (the engine's `LoadImage(name, lookForAlpha=true)`): after loading the
   base, it builds `dir\` + `"_"` + `filename` (`DAT_005B0F58` = `"_"`) and loads that too. If the
   base failed but the companion loaded, the companion *becomes* the image with RGB forced to white
   and alpha taken from its channel 0. Otherwise, if the two are the same size, it copies the
   companion's channel-0 byte into the base's alpha byte, pixel by pixel, and frees the companion:
   ```c
   for each pixel i: base.a[i] = mask.b[i];   // ARGB dword: byte 3 <- mask byte 0
   ```
   So **alpha comes from the mask's blue channel only** - the mask is a grayscale silhouette, and
   its RGB is discarded. 187 of 246 images rely on this convention (`_guppy_swim1.gif`, ...).
2. **Explicit attributes** in the manifest, resolved like any other path (default `path` +
   value, same extension probing). Both forms were measured against the shipped art
   (`extraction.json` + `System.Drawing` on the mask files):
   - `alphaimage="tankbackdrops_"` - mask **sized like the whole base image**
     (`tankbackdrops_.gif` 190x121 = base 190x121, `eggbonus_.gif` 96x121 = base, `aatop_.jpg`
     32x37 = base, `_mbuttono.gif` 57x60 = base on `MENUBTND2`);
   - `alphagrid="mainbutton_"` - mask sized like **one grid cell** (`mainbutton_.gif` 90x29
     against a 270x29 `cols=3` sheet, `leftbutton_.gif` 63x29 against 189x29), applied to every
     cell.

   The `alphagrid` path is the one decompiled: `FUN_004189B0` loads the mask from the entry with
   the *same* `LoadImage(mask, true)` call (so a mask can even pull its own `_` companion), divides
   the base by `cols`/`rows` to get the cell size, requires
   `mask.width == cellW && mask.height == cellH` - otherwise it throws
   `"GridAlphaImage size mismatch between <base> and <mask>"` - and then walks
   rows -> columns -> cell pixels, copying mask channel 0 into the base alpha byte, and finally
   marks the image dirty (base vtable slot 25).

   Unified rule: **the mask must match the unit it masks** - the sheet for `alphaimage`, one cell
   for `alphagrid`. The two attributes only diverge when `cols*rows > 1`, and every `alphaimage`
   entry in the shipped manifest happens to be single-cell, so the distinction is invisible in this
   game's data.

17 entries declare one of the two explicitly; 204 of 246 images have a literal mask file on disk;
only `SLIDERTHUMB`, `HELPALIEN` and `HELPPETCHOOSE` carry their transparency in the GIF itself
(P3.2). `EDITBOX`'s mask (`96x33` against a `90x42` cell) is the one size mismatch in the set - it
is a source-asset inconsistency, not an engine special case, and P3 already records it.

The mask is applied **per cell, after slicing** for `alphagrid`, and **once, before slicing** for
`alphaimage`. For P4 that means: `AtlasTexture` per cell + a `mask` layer per cell (or a baked RGBA
PNG per cell at build time - the committed `frames/<ID>/fNNN.png` output already bakes base+mask,
which is the cheapest correct option). Because the mask is *cell*-sized for `alphagrid`, a baked
per-cell PNG is strictly better than a runtime texture pair: the engine re-reads the same mask
cell for every frame of the sheet, so there is nothing to gain from keeping it separate.

`parse-resources.ps1` records the same three roles in `extraction.json` (`maskRole` =
`alphaimage` | `alphagrid` | `candidate` | `selfMask`), so the build side already distinguishes
them - the P4 runtime does not need to.

### 5.4 What `-1` in `framemap` means

`MERYLBLINK` is `cols=3 anim=once framemap="0,1,2,1,0,-1" perframedelay="3,2,3,1,1,1"`. The map
has six steps for a three-cell sheet, and `-1` is the sixth - so it is not a terminator (the
parallel `perframedelay` list also has six values) and it is not a frame index. The reading that
fits the art and the engine's slice model is **"hold the previous frame"**: an explicit dwell step
that lets the blink sit on the open-eye pose for one extra tick without repeating the index. The
animation builder (§5.2) does not special-case negatives - it stores the map verbatim and only uses
its length - so the decoding has to be in the frame-advance path (P2.2's animated-image update,
Q-0032). P3.5 currently *skips* negative entries (`gen_spriteframes.gd`), which for this one
animation shortens the blink by one step - harmless on screen, but a real (if invisible) divergence.

## 6. `<Font>` and `<Sound>` entries

- **Font** (`path` only): the file is a PopCap bitmap-font descriptor (`.txt`), read by
  `Sexy::FontRes`. 15 fonts, all under `data\`, sizes encoded in the file, no per-entry attributes
  beyond `id`/`path`. P3.6 already converted them.
- **Sound** (`path`, plus `volume` and `alias`):
  - `volume` - a float 0..1 stored as the resource's default playback volume; 7 entries declare it
    (`EXPLODE` 0.75, `HIT` 0.75, `NIKOOPEN` 0.5, `NIKOCLOSE` 0.5, `RICOCHET` 1.0, `ZAP` 1.0,
    `ZZAM` 0.8). It reaches `SoundRes` exactly where EV-0149 note 2 describes (the double at
    `+0x70`, applied through sound-manager slot 6 when positive).
  - `alias` - two entries: `AWOOGA` aliases `START`, `ZZAM` aliases `END`. This is the manifest
    analogue of the music layer's track ids: the alias is the *semantic* name the code asks for,
    the id is the file. Nothing else in the manifest uses aliases, and no code path was found that
    resolves an alias - so it is a data-side convenience, and P4 can ignore it.
  - Sound ids are *not* stable indices: each `SOUND_*` id is fetched once at startup and memoised
    in a dedicated global (the 65-entry table in `p2.14-sound-table.txt`). P4 must not assume
    `SOUND_ZAP` is index N.
  - One naming oddity worth knowing when regenerating assets: `FONT_CONTINUUMBOLD14OUTLINE` loads
    `data\ContinuumBold14Outback.txt` - the file name does not match the id.

### 6.1 Entry creation vs entry loading

Parsing an `<Image>`/`<Sound>`/`<Font>` element only *registers* an entry: it builds the record with
its id, path(s), grid and flags, leaves the payload at `entry+0x6C` empty and its "loaded" byte at
`entry+0x68` clear. The actual file load is `FUN_00419480(entry)`, which dispatches on the entry
kind:

| entry kind | test | load |
| --- | --- | --- |
| Sound | `+0x88 == 0` and the path does not start with `!ref:` | `FUN_0045CC30` (the `SoundRes` path of EV-0149); failure falls back to a stub sound object so gameplay never sees null |
| Image | `+0x88 != 0` | vtable slot `0x104` of the manager's owner with the base path and `lookForAlpha = 1` |
| Font | `+0xAC != 0` | `FUN_00467560(path, three flag bytes)`; the result must RTTI-cast to `ImageFont` with a non-null glyph map |

Three behaviours fall out of that code:

- **Failure messages** are per kind: `"Failed to load image: %s"`, `"Failed to load font: %s"` (and
  the sound stub path). Unlike the manifest errors these are *not* fatal - the entry stays unloaded
  and the game continues, which is why a missing asset is a missing sprite rather than a crash.
- **`!ref:` font references.** A font whose path begins with `!ref:` is not a file: the loader skips
  five characters and calls `GetFont(rest)` (`"Ref font not found: "` on failure). The shipped
  manifest never uses it (0 occurrences), so it is a framework feature, not game data.
- **Font extra list.** A non-empty third string on a font entry is `strtok`-ed on `", \r\n\t"` and
  each token is fed to font vtable slot `0x48` before slot `0x58` closes the set. No shipped font
  entry has any attribute beyond `id`/`path`, so this is unused here.

On success the payload is stored at `+0x6C`, the loaded byte is set, and the manager vtable slot
`0x34` is called to notify (the loader-progress bookkeeping behind the bar).

## 7. The registry and the typed lookups

The manager keeps **three separate maps** keyed by full id - images at `manager+0x10`, sounds at
`+0x1C`, fonts at `+0x28` - and each entry is a small record holding the id, the path, the grid and
flags, the loaded payload (`+0x6C`, an object pointer for images/fonts, the pool id for sounds) and a
"loaded" byte at `+0x68`. Three typed accessors sit in the manager's vtable and are the only way
gameplay touches resources:

| slot | call | returns |
| --- | --- | --- |
| `+0x40` | `GetImage(id)` = `FUN_00419D50` | borrowed `Sexy::Image*` (`ImagePtr` AddRef/Release around it) |
| `+0x44` | `GetSound(id)` = `FUN_00419F40` | sound-pool id, a plain int (`-1` = not loaded) |
| `+0x48` | `GetFont(id)` = `FUN_0041A080` | borrowed `Sexy::Font*` |

`GetImage`/`GetSound` share one pattern: look the id up, and if it is present but its payload is
still empty, return it anyway **when `manager+0xB0` is set and the entry's `+0x68` flag says
"deferred"** - that is the loading thread in progress, where a placeholder is legitimate. Only when
there is no entry at all (or neither condition holds) does the accessor throw. That is the mechanism
behind the game booting its own loading screen: `Init` ids are real, everything else is a
not-yet-filled record until the thread reaches it.

A miss throws `"Image resource not found: %s"` / `"Sound resource not found: %s"` /
`"Font resource not found: %s"` (strings at `0x5B00C0`, `0x5B00E0`, `0x5B0100`; the throw sites are
`0x419E47`, `0x41A003`, `0x41A13E`). There is no null return and no "missing texture" substitute: a
typo in an id throws at the first lookup, and for the group handlers the first lookup is startup.
That is why the group handlers are effectively generated from the manifest - and why the 326/326
cross-check above is such a strong result.

The call shape throughout the game is `global = GetImage("IMAGE_X")` once at group load, then
`global` used directly - no per-use lookup, no string keys at runtime. Refcounts are handle-based
(`FUN_004682B0` copy, `FUN_004681E0` drop) and the images themselves are freed when the last handle
goes; the group globals therefore stay valid for the process lifetime.

## 8. Implementation spec for P4

1. **No runtime manifest parsing.** `tools/parse-resources.ps1` -> `extraction.json` is the pipeline
   of record; P4 reads that (or the generated `.tres`/resource files), never `properties\resources.xml`
   at runtime. The engine's parser is fatal-on-first-error and case-sensitive in its id lookups;
   nothing in Godot should reproduce that brittleness.
2. **Keep the three groups as load phases.** `Init`-equivalent (loader screen + cursors + default
   font + click sound) must exist before the first frame, `Register`-equivalent (dialog skin, UI
   fonts) before any dialog/menu, `LoadingThread` behind the loading bar. This is a real, observable
   ordering constraint: the original cannot draw its own loading screen without `Init`.
3. **Ids stay ids.** Keep `IMAGE_*`/`SOUND_*`/`FONT_*` strings as the resource keys (they are also
   the ids used in every other P2 note), and resolve them once into typed handles at boot, exactly
   as the group handlers do - never per-use.
4. **Frame model.** `cols`/`rows`/`cellW`/`cellH` per sheet, row-major cell order, `framemap`
   applied as the playback order. `anim`: `loop` -> `SpriteFrames` looping animation, `once` -> play
   once then hold the last frame, `pingpong` -> the engine's own expanded `0..N-1,N-2..1` sequence
   (exact) or Godot's `pingpong` mode (equivalent apart from one frame at each turn). Non-animated
   grids get a plain frame array for manual indexing.
5. **Delays.** Treat one `framedelay` unit as one 10 ms logic tick (P2.1's clock; Q-0032b keeps the
   unit formally open), so `2` -> 20 ms and `4` -> 40 ms; `perframedelay` overrides per position in
   the mapped sequence and defaults to `framedelay` when short; `begindelay` = hold the first frame
   that many ticks before starting. Do this in the animation player, not by re-timing the sprites.
6. **Alpha.** Prefer the baked per-cell RGBA PNGs P3.5 already produces. If a mask has to be applied
   at runtime, reproduce "alpha = mask blue channel" - do not use the mask's luminance and do not
   multiply colours by it.
7. **`alphagrid`** masks are cell-sized and tile across the sheet; `alphaimage` masks are
   sheet-sized. Both are already resolved by `parse-resources.ps1`; nothing at runtime needs to
   guess `_`-prefixed companions.
8. **Sounds.** Map id -> `AudioStream` once (`SfxPool` from P2.14 §8.6) and apply the entry's
   `volume` as the pool default. Ignore `alias`.
9. **`ddsurface`** (the six `AQUARIUM*`) is a DirectDraw optimisation with no Godot meaning; the
   `nopal`/`a4r4g4b4`/`a8r8g8b8`/`nobits`/`minsubdivide` flags are loader hints for the same
   layer. Do not port any of them.
10. **Do not port:** the XML parser, the extension-probe chain (bake the resolved paths), the
    refcount handles, and the `variant` attribute (parsed and thrown away by the engine itself).
