## 2. Timestep model (the key finding)

`FUN_0049f1b4` is a **fixed-timestep game loop with catch-up**, using the WinMM millisecond
clock (`timeGetTime` at IAT `0x5163f8`):

```
interval = this[0x44]            # ms per logic tick
last     = this[0x50]            # last processed tick time (ms)
guard    = this[0x48]            # byte flag: allow catch-up sleep when set
do up to 10 single-tick updates per Process() call:
    now = timeGetTime()
    if (now - last < interval):
        call virtual [vtable+0x1c]()          # per-frame update/draw step
        last += interval                      # advance fixed grid
        if (now - last > 1000) last = now - 1000   # clamp if far behind
        frames++
    else:
        if frames_done > 0: sleep(interval - (now - last))  # catch-up throttle
        break
call FUN_0049eac9 (widget cleanup)
```

- The update virtual is dispatched via `(**(code **)(*this + 0x1c))()` at `0x49f344`; a second
  virtual `[EAX+0x20]()` at `0x49f375` returns a bool (stop/continue). `+0x1c`/`+0x20` are
  **vtable slots of the concrete `SexyApp`/`LuaApp` class** - re-verified live per run.
- The loop runs at most **10 logic iterations per message**; typically 1 (message pump is fast
  enough that only occasional catch-up happens).

Runtime-probed facts (FPS overlay, `0x49fdf1`):
- `DAT_0055fbb8` counts **actual `Process()`-loop iterations**, reset to 0 every 1000 ms
  (`CMP`+`FADD` path; `IMUL EAX,EAX,0x3e8` then divide by elapsed → FPS display).
- `[0x539e78]` = `0.5` double - FPS rounding constant before int conversion.
- The 1000 ms threshold test in the FPS timer uses a real-valued compare (`FNSTSW` at
  `0x49fef0`); the threshold is not a stored double (baked in FPU sequence).

## 3. Timing primitives (for P4)

- **Logic clock:** WinMM `timeGetTime()` (ms, 32-bit wrap). No `GetTickCount`/QPC in the tick
  loop itself.
- **Precision timer class** (used by FPS overlay and gameplay-side timers; fields: `+0x8`
  double seconds, `+0x10` initialized byte): reset = QPC; elapsed = double seconds.
- Actual render cadence equals message availability: the DRM window has a 100 ms `SetTimer`
  (`0x4067cd`), but the game loop does not depend on it for logic - `Process` is driven by
  every window message + the WM_TIMER path.

## 4. What this does NOT establish

- Whether Lua gameplay scripts define their own per-frame hook (likely `LuaApp` overrides the
  `+0x1c` virtual and runs `Update`/`Draw` - **P2.2/P4 follow-up**).
- The FPS *target* in practice on original hardware (100 ticks/s is the loop cap; rendering is
  message-driven).
- The `mUpdateMultiplier = 0.85` consumer is not located yet (probably animation dt scaling in
  `UpdateFrames`) - follow-up when P2.2+ touches animation timing.
- `0xb2`/`0xb3`/`0xb1` flag semantics.

## Implementation spec for P4

- Mirror the loop as a **fixed 10 ms logic tick** (100 Hz) decoupled from render: accumulate
  real dt, run `update()` per 10 ms slice, render once per frame (or on demand); cap catch-up
  at 10 slices per frame; clamp accumulated backlog to 1000 ms.
- `frame_delay` values in `resources.xml` (`framedelay`, `begindelay`, `perframedelay`) are
  manifest-side animation delays; their unit is now best modeled as **1/100 s per unit**
  (each frame delay unit = one 10 ms logic tick) - **re-verify in P2.2 when animation update
  order is confirmed**; do not bake into `.tres` (P3.5 left them raw in `extraction.json`).
- Use a monotonic ms clock (Godot `Time.get_ticks_msec()`), convert elapsed to double seconds
  for timer math; keep the 0.85 multiplier per-tick (animation smoothing factor).
- Debug FPS overlay: draw `FPS: %d` over the scene, computed per 1000 ms window
  (nice-to-have; flag/shortcut not yet recovered - string only).
