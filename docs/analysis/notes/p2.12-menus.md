## 0. Method: from a class to its constructor

The RTTI dump (`p2.2-module-rtti-classes.txt`) lists **two vtables per screen class**: a 7-slot one
and a 64-slot one. `xrefs` on a vtable address returns a plain address list, and for every screen
checked it contains **exactly two code writers**: the destructor and the constructor. Decompiling the
writer that is not the destructor therefore yields the constructor directly - no string hunting.

| class | 7-slot vtable (ButtonListener) | 64-slot vtable (object) |
| --- | --- | --- |
| `Sexy::TitleScreen` | 0x5A20E4 | 0x5A2104 (writers 0x51C169 dtor, 0x52EB94 ctor) |
| `Sexy::GameSelector` | 0x5A2220 (writers 0x51C300 dtor, 0x52E0C1 ctor) | 0x5A2244 (writers 0x51C2FA dtor, 0x52E0BB ctor) |
| `Sexy::StoreScreen` | 0x5A1630 | 0x5A1654 (writers 0x51954B dtor, 0x52B31F ctor) |

`0x52E0C1`, `0x52E0BB`, `0x52EB94` and `0x52B31F` all sit inside the constructor bodies transcribed
below, which confirms the rule. The same query can be replayed for the remaining screens
(`HelpScreen` 0x5A0A20/0x5A0A44, `HighScoreScreen` 0x5A0B60/0x5A0B84, ...).

## 1. Two-vtable convention (settles the `+0x88` / `+0x8C` split)

Every screen class is a `Sexy::WidgetContainer`-style object **plus** an embedded
`Sexy::ButtonListener` at `+0x88`:

| offset | contents |
| --- | --- |
| `+0x00` | object vtable (64 slots) |
| `+0x88` | ButtonListener vtable (7 slots: dtor + 6 callbacks) |
| `+0x8C` | manager pointer |

Both constructors store the manager at `in_ECX[0x23]` (= `+0x8C`), and the ButtonListener callbacks
receive `this = object+0x88`, so inside a callback the manager is `[this+4]`. That is exactly what
`FUN_0051F160` does, and it reconciles the earlier inconsistency: the single-vtable gameplay classes
(fish/alien/missile) put the manager at `+0x88` (P2.8), the two-vtable screen classes at `+0x8C`
(P2.11 tank update, and every screen here).

The 7-slot layout is fixed: slot 0 is the deleting destructor, slots 1-6 are the six ButtonListener
callbacks, and every slot a class does not override points at the **same shared no-op `0x46C690`**
(e.g. `ButtonListener::vftable` 0x5A0680 = `46CA30, 46C690 x5, 49B300`). A class that overrides only
slot 2 - like `GameSelector` - handles one callback and inherits the rest.

## 3. `Sexy::TitleScreen` (ctor 0x52EB50, dtor 0x51C140)

```c
FUN_0052EB50(manager):                                  /* TitleScreen ctor */
    *this = TitleScreen::vftable;                       /* +0x00 object vtable */
    this[0x22] = TitleScreen::vftable;                  /* +0x88 ButtonListener vtable */
    this[0x35] = manager;                               /* +0xD4 */
    std::string at +0xA8 = "";                          /* capacity at +0xBC */
    this[0x23] = new ImageWidget(0, &this[0x22]);       /* +0x8C, image DAT_005e8E40 */
    ...                       /* +0x120/+0x130 tint colours, vtable[0x7C](0) */
    this[0x24] = new ImageWidget(1, &this[0x22]);       /* +0x90 */
    this[0x24]->label = "Click Here To Register!";
    this[0x24]->rect = (0, 0, w + 0x14, h + 0x14);      /* measured from the image */
    if (app[0x71C] != 0 || thunk_00479FC0() != 0 || app[0x71D] != 0)
        this[0x24]->vtable[0x7C](0);                    /* hide the register button */
    else FUN_0052D2E0();                                /* registration prompt */
```

The destructor (`FUN_0051C140`) restores both vtables, deletes the two children at `+0x8C`/`+0x90`,
frees the `std::string` at `+0xA8` (capacity at `+0xBC`, length at `+0xB8`) and calls the base
`FUN_0046DD50`. `0x51C2A0` is the scalar-deleting wrapper around it, and it is exactly slot 0 of
TitleScreen's 64-slot vtable - the check that the two-vtable read is right.

The ButtonListener overrides at slots 1 and 2 are `0x51AA30`/`0x51AA50`; both forward to the app:
`(*DAT_005EB6A4)->vtable[0xD8](DAT_005E8C40)`. So the title screen has no menu logic of its own -
clicks are pushed into the app object.

## 5. The mode writer - `FUN_0051F160` (Q-0024 answered) (EV-0132)

`FUN_0051F160(button_id)` is slot 2 of GameSelector's 7-slot ButtonListener vtable (0x5A2220). It is
`this = selector+0x88`, so `[this+4]` is the manager.

```c
FUN_0051F160(int id):
    manager+0x880 = 0;                        /* demo flag cleared on every button */
    switch (id) {
    case 1: manager+0x87C = 0; goto START;    /* Adventure */
    case 2: manager+0x87C = 5; goto START;    /* Virtual Tank */
    case 3: FUN_0054C620(1); return;          /* Options dialog */
    case 4: FUN_005517F0(); return;           /* Quit */
    case 6: FUN_005522D0(); return;           /* Hall of Fame */
    case 7: FUN_0054C220(0); return;          /* Help */
    case 8:                                   /* Time Trial */
        if (profile[0x1C] < 2 && profile[0x59] == 0) goto NOT_YET_1;
        manager+0x87C = 1;
        goto START2;
    case 9:                                   /* Challenge */
        if (profile[0x59] == 0) goto NOT_YET_2;
        manager+0x87C = 4;
        goto START2;
    case 9999: FUN_0054B5F0(); return;
    default: return;
    }
  START:
    FUN_0054B360();                           /* tear down the object at manager+0x738 */
    FUN_00552380(1, 1);                       /* level-start dispatcher */
    return;
  START2:
    FUN_0054B360();
    if (FUN_0054CB20() == 0) FUN_0054C130();  /* follow-up only when there is no VT tank */
    return;
  NOT_YET_1: app->vtable[0x120](0xE, 1, <3 strings>, 3);   /* "Not Yet!" dialog */
```

Consequences:

1. The writer of `[manager+0x87C]` **is** the title menu, and it writes exactly four values:
   0 (Adventure), 1 (Time Trial), 4 (Challenge), 5 (Virtual Tank). Modes **2 and 3 (Sandbox) have no
   writer** anywhere in the corpus, so Q-0014 stays open and Sandbox's name still rests on the UI
   text alone.
2. Adventure and Virtual Tank take the `START` path (`FUN_00552380(1,1)`), while Time Trial and
   Challenge call `FUN_0054B360()` + `FUN_0054CB20()` first and only fall into `FUN_0054C130()` when
   there is no Virtual Tank to resume. The asymmetry is real code, not a decompiler artifact: the two
   gated modes are the ones with a persisted record file.
3. **Every** mode button clears `manager+0x880` (the demo flag), confirming EV-0130's reading that
   the flag marks the attract/demo session and is dropped as soon as a menu action starts.
4. The Time Trial gate is `profile+0x1C < 2 && profile+0x59 == 0` (must be past tank 1, i.e. the
   second tank is unlocked), the Challenge gate is `profile+0x59 == 0` (Adventure finished). Both
   show the same 3-string "Not Yet!" dialog through `app->vtable[0x120]` slot 72
   (`0x120/4 = 0x48`) with kind 0xE.
5. Button ids 3/4/6/7 are **not** mode buttons: options, quit, hall of fame, help. `FUN_005517F0()`
   (id 4) is the quit confirmation: message "Stop the insanity?", empty title and a "Quit" button
   (`DAT_005a5BF4`, the same literal as the button label) through
   `app->vtable[0x120](0xB, 1, <strings>, 2)`.

The 8 item rects, in creation order (an 8-entry `CRect` array on the stack, x/y/w/h):

| item | rect | item | rect |
| --- | --- | --- | --- |
| 0 | 1, 5, 109, 140 | 4 | 303, 38, 98, 140 |
| 1 | 1, 143, 109, 140 | 5 | 414, 38, 98, 140 |

The row x positions are built from `+0x1C4`/`+0x1C8` (`192 + n*111`), i.e. `0xC0` is the first
column and `0x6F` the pitch - not a 192x111 cell. The three left-column items and the single
bottom-right item are drawn from the same array, so the "8 slots" are not a uniform grid; the exact
widget-to-rect binding goes through `vtable[0x9C]` with the argument lost in a register, so the table
above is the **creation order**, not proof of which slot is which.

The Shell counter is a plain `Sexy::MyLabelWidget` (`FUN_00534600`): empty string (capacity
`+0xA0`), a default font/colour from `FUN_00433300()`, a placeholder rect at `+0xA4` and a font at
`+0xB8` - the StoreScreen then overwrites the rect with (250,155,150,255) and the font with
`DAT_005e8CE4`. `FUN_005346D0(str)` is the label's **setter**, not a formatter: it assigns the
string through `FUN_00422210` and then calls `vtable[0x44]` (slot 17, the "text changed / reformat"
hook that `MyLabelWidget::SetText` uses), so the `sprintf(+0xC4, "%d")` in the ctor is what produces
the shell count text (EV-0135).

The items are `Sexy::StoreButtonWidget` (vtable 0x5A719C, RTTI row 118) built by
`FUN_005331A0(id, listener, data)`, which chains the `FUN_00475090` image-button base ctor and then
fills fixed fields - no profile read, no price array read, no affordability test:

### 6b. `Sexy::StoreButtonWidget` - the five overrides (EV-0135)

Dumping the whole 64-slot vtable shows exactly five entries outside the shared `Sexy::` base ranges
(`0x46B...`-`0x46E...`) - and they are **not** the slots the first pass guessed (21/26/41/48/49):

| slot | byte offset | target | behaviour |
| --- | --- | --- | --- |
| 22 | 0x58 | `FUN_00531A30` | base `thunk_FUN_0046C4F0`, then forwards to the child at `+0x124` slot `0x138` |
| 26 | 0x68 | `FUN_00531A60` | draws the item art, 5 kinds on `+0x14C` |
| 44 | 0xB0 | `FUN_00531C30` | draws the price line from the string at `+0x12C` |
| 50 | 0xC8 | `FUN_005319B0` | base `FUN_00475930`, then `store+0xBA8 = [this+0x88]`, `store+0xBAC = 0` |
| 51 | 0xCC | `FUN_00531A00` | base `FUN_004759E0`, then `store+0xBA8 = -1` |

`FUN_00531A60(mode)` (slot 26) draws the item art; the kind at `+0x14C` selects the branch, and the
whole switch is skipped when the byte at `+0x55` is 0:

| `+0x14C` | drawing |
| --- | --- |
| 1 | forwards to the child widget at `+0x124`, slot `0x13C`, with a second argument `cVar2` (`0`, `1` or `2` from `2 < id`, `6 < id`) |
| 2 | `FUN_00456950(DAT_005e8c80, 0x23, 0x17, 0)` - Bubbulator icon |
| 3 | `FUN_00456950(DAT_005e8a60, 0, 0, [+0x158])` - backdrop, scaled by `+0x158`; if `+0x59`/`+0x58`/`+0x148` is set it is redrawn additively in `0x323232` |
| 4 | `FUN_00455D20(DAT_005e8c68, 0x1E, 0x14)` - alien attractor icon |
| 5 | `FUN_00456980(DAT_005e8aa0, 0x28, 0x28, ([+0x28] / 4) % 10, 2)` - food upgrade level digit |

The two special data pointers are translated before drawing: `DAT_005e8c5c` by `FUN_004563D0(15,4)`
and `DAT_005e8c78` by `FUN_004563D0(0,5)`; the same pair is special-cased in the price drawer.

`FUN_00531C30` (slot 44) draws the price line. It centres on `+0x150` (13) and sits on `+0x154`
(108), measures the string at `+0x12C` with `vtable[0x1C]` and draws it with `FUN_00455CF0`:

- normal: text colour `FUN_00433360(0x6E,0xFA,0x6E)` plus the price icon `DAT_005e8c3c` at

- **greyed out**: when the byte at `+0x55` is 0 - colour `0xCCCCCC`, no icon, and the text drops to

- **highlighted**: when `+0x59`, `+0x58` or `+0x148` is set - colour `FUN_00433360(0xF0,0xFF,0xC1)`

writes its own id (`[this+0x88]`) into `store+0xBA8` and clears the hover timer `store+0xBAC`, and
the "leave" handler resets `store+0xBA8` to -1.

### 6d. The stock refresh - `FUN_0052FEA0` (EV-0135)

The StoreScreen ctor never populates anything; the whole stock is rolled by `FUN_0052FEA0(extra)`,
which slot 20 (attach) calls with 0:

```c

    manager = [this+0x8C];                        /* this = +0x88 listener, manager at +0x8C */

    FUN_0040AE50(profile[0x98] + t);               /* seed the store RNG */
    FUN_00501490(+0xB98, +0xB9C);
    FUN_00519EB0(); FUN_00519F70(); FUN_0052FE10(); FUN_0052F0D0();
    for (i = 0; i < 8; i++)
        if (profile[0xA8 + i] == 0 && item[i]+0x14C != 0) FUN_005363D0(item[i]);  /* buyable */
        else                                             FUN_005372F0(item[i]);  /* SOLD      */
```

- `FUN_0052F0D0` is the stock roller proper. It spends the three one-off unlocks first - if
  `profile+0x90 == 0` -> `FUN_00537230(2, 0, 20000)`, else if `profile+0x94 == 0` ->
  `FUN_00537230(4, 0, 50000)`, else if `DAT_005e89dc == 0` -> `FUN_00537230(5, 0, 20000)` - and
  otherwise fills the slot through `FUN_0051C0B0(2)` / `FUN_0052B800(2)` / `FUN_0051B260(0,-1,9)`
  plus a second `FUN_0051B260(1,-1,9)` slot, each with a coin-flip `FUN_00519D30(obj, 0)`. It then
  walks `profile+0x72+i` for `i = 0..5` and, for every clear flag (with an extra `rand%5 == 0` gate on
  `i == 5`), calls `FUN_00420260(&i)`.
- `FUN_00519EB0` / `FUN_00519F70` / `FUN_0052FE10` build the icon/text children: two 0x230-byte
  objects per helper, each handed to `FUN_00537290(obj, FUN_00519730())`. `FUN_0051B260(flag, id)` is
  the object factory - a 76 % ordinary branch (`FUN_00519E00`) and otherwise a weighted roll over
  eight pet ids (8/9/7/10/6/0x24/0x23/0x22 at weights 26/25/25/10/5/3/3/3) that constructs one of
  `FUN_004EC0F0`, `FUN_004EA7B0`, `FUN_004EF9A0`, `FUN_004EE530`, `FUN_004F02A0`, `FUN_004F0630`,
  `FUN_004F0570`, `FUN_004F01E0` - i.e. the kind-1 slot sells a **random pet**. The two helpers beside
  it are the fixed-pet path: `FUN_0051C0B0(kind)` walks `Tank+0x108` and answers "is pet `kind`
  already in the tank" (`entity->type->[+0x124] == kind`), and `FUN_0052B800(kind)` builds that pet
  outright (0 Rocky, 1 Ludwig, 2 Cookie, 3 Johnny V., 4 Kilgore, each stamped with `[pet+0x124] =
  kind`). `FUN_0052F0D0` uses the pair as "hand out Cookie once, roll randomly after that".
- `FUN_00519730()` is that pet's price getter: it switches on a kind at `+0x8C`, reads the two flags
  `+0x1D0`/`+0x1D1` and the current tank from `FUN_00501060()`, and returns a flat 25000/30000/40000/
  50000 for tanks 1-8, otherwise a kind-based price (10000 for 6 and 0x24, 3500 for 7, 2500 for 8/9,
  5000 for 10, 15000/20000 for 0x22/0x23, 25/500/2500 for 0 and 0/1000/5000 for 5). The decompiler
  loses the `ECX` binding at all four call sites, so "the receiver is the rolled pet" is inferred
  from the fields, not proven - recorded as such in Q-0018.
- `FUN_00537290(child, price)` installs the **kind-1** slot: it destroys the previous child
  (`child->vtable[0](1)`), stores it at `+0x124`, writes `child+0xE0 = price`, sets `+0x14C = 1` and
  the price line; with `child == 0` it clears `+0x124`, sets `+0x14C = 0` (sold out) and the price to 0.
- `FUN_00536350(price)` is `SetPrice`: `[item+0x128] = price`, then `sprintf(buf, "%d", price)`
  (`FUN_004120C0` with `DAT_005adec0` = `"%d"`) and the result is assigned to the widget's string via
  `FUN_00422210`. **The price line is a bare number** - the coin/shell glyph next to it is the
  `DAT_005e8c3c` icon that slot 44 draws at `(x+0x19, y+3)`.
- `FUN_005363D0(item)` is the **buyable** branch: `byte[item+0x55] = 1`, then the price line is reset
  from the last price `[item+0x128]` (100 in the ctor) through `FUN_00536350`.
- `FUN_005372F0(item)` is the **unavailable** branch: `FUN_00537290(0,0)` (drops the child and sets
  kind 0), `FUN_00532EC0(0)`, `byte[item+0x55] = 0`, and the widget's string is overwritten with the
  4-character literal **`SOLD`** (`0x5A7CA4`) via `FUN_00426BE0`.

That closes Q-0018: the string at `+0x12C` that slot 44 draws is either `"%d"` of the price or the
literal `SOLD`, the grey path of slot 44 is exactly `+0x55 == 0` (the sold-out state), and the kind at
`+0x14C` is written by `FUN_00537290` (1) or `FUN_005372F0` (0). New profile fields seen here:
`profile+0xA8..+0xAF` (8 per-item "already bought" bytes), `profile+0x72..+0x77` (6 pet-slot flags
used by the roller), `profile+0x90` / `profile+0x94` (the two one-off unlock gates) and
`profile+0x98` (store RNG seed).

- The 24-byte clear at `profile+0x5A` is the same array P2.6 §1.5 reads to instantiate pets at level

  pet selection on level start until it is resolved.
- `profile+0x18` is compared against the second return word of `FUN_0054B2A0()` (Ghidra's

  carries `+0x1C` onwards), so treat the comparison as "current tank < unlocked tanks" only as a
  reading, not as evidence.

## P4 implementation spec

1. **Screen base.** Implement one `Screen` base = widget container + listener mixin, keeping the two
   vtables distinct in the port as two components: `ScreenNode` (draw/update/children) and
   `ButtonListener` (6 callbacks, all no-ops by default). Buttons are widgets with `id`, three
   bitmaps and a rect; text buttons carry a label + font.
2. **Title.** Two image buttons: "story time" (art) and "Click Here To Register!" (hidden when the
   profile flag at `app+0x71C`/`+0x71D` is set). Both forward to the app, no local logic.
3. **Main menu.** Eight buttons at the rects in §4. The mode buttons write the mode and call the
   level-start dispatcher; the four others open options / quit / hall of fame / help. Clear the demo
   flag on **every** press. Gate Time Trial on "second tank unlocked" and Challenge on "Adventure
   finished", showing the "Not Yet!" box otherwise. Ids 2/8/9 are the only mode writers - do **not**
   invent a Sandbox entry.
4. **Store.** 8 item slots with the rects in §6, a Shell counter at (250,155,150), a 640x480 frame
   overlay and a 100-249 tick refresh timer. Each slot carries an item kind (`+0x14C`: 0 sold out,
   1 egg/pet, 2 Bubbulator, 3 backdrop, 4 alien attractor, 5 food upgrade), a price line string
   (`+0x12C`, `SOLD` when unavailable) and an enabled byte (`+0x55`) that greys the line to
   `0xCCCCCC`. Re-roll the stock on attach (§6d) and on every refresh-timer expiry. In Virtual Tank,
   bypass `BuyItem` for actions 0-0xB and route action 10 to the pet store; route 0xF to the egg
   handler in every mode, and gate the egg on the boss being dead (documented divergence, Q-0021).
5. **Dialogs.** One modal container: create, measure, place at the caller's rect, push on the app
   window stack, with a 3-string message box for refusals.
6. **Open work.** The price formatter behind the buyable branch (`FUN_00536350`) and the helper
   plumbing it shares with the roller (`FUN_00519730`, `FUN_00537290`, `FUN_00519D30`,
   `FUN_0051B260`, `FUN_0051C0B0`, `FUN_0052B800`), the remaining screens' ctors (same
   vtable-xref recipe), and the pet-selection clear (Q-0025).
