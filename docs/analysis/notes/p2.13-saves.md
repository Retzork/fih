# P2.13 - Save/profile formats (partial)

Status: **in progress** (2026-10-21). Location, `users.dat`, and the full
`user%d.dat` field order are located. Tank-save field semantics and the
trophy/story binding remain open.

Primary evidence: EV-0108 (early local sample), EV-0109 (GameBanana sample +
`user%d.dat` serializer map). Samples live under
`docs/analysis/inputs/p2.13-saves-2026-10-21/` and
`docs/analysis/inputs/p2.13-saves-gamebanana-100/`.

## 1. Locations and file roles

- Live user data: `C:\ProgramData\Steam\Insaniquarium\userdata` (not the game
  install folder).
- `users.dat` - profile list. Serializer `FUN_00513850`; list load/save
  `FUN_00514C00` / `FUN_00514D50`.
- `user%d.dat` - one profile slot. Load `FUN_005145A0`, save `FUN_00514730`,
  shared field serializer `FUN_00503730`.
- `adv%d.dat` - Adventure tank save. Writer `FUN_00546990`, tank serializer
  `FUN_00546240`; version dword `0x36`.
- `sim%d.dat` - observed in the GameBanana pack, same version and tank-save
  family as `adv%d.dat`; the `sim` prefix semantics are not proven.
- `scr%d.dat` - separate Shells-persistence file
  (`FUN_005148C0`/`FUN_00515910`), not the Adventure save.
- `highscores.dat` - string present in the module; format not parsed.

## 2. `users.dat`

Observed layouts:

| Sample | Bytes | Layout |
| --- | --- | --- |
| early local | 22 | `0E 00 00 00` \| `01 00` \| `06 00` \| `okokok` \| `01 00 00 00` \| `01 00 00 00` |
| GameBanana | 21 | `0E 00 00 00` \| `01 00` \| `05 00` \| `Roman` \| `04 00 00 00` \| `01 00 00 00` |

- `0x00` dword = `0x0E`; `FUN_00513850` compares it with `DAT_005e042c`, so it is
  a version/format value, not a count.
- `0x04` uint16 = profile count (1 in both samples).
- `0x06` uint16 = name length; the name follows as raw bytes.
- Two trailing dwords follow the name. They are `1,1` in the early sample and
  `4,1` in the GameBanana sample. Their meaning is **unresolved**; do not label
  the first one as a constant user ID.

The registry value `HKCU\Software\PopCap\Insaniquarium\CurUser` selects the active
profile name. The early sample stores `okokok` (6 characters), not `okokokok`.

## 3. `user%d.dat` - 232-byte profile slot

`FUN_00503730` is the single field serializer used by both load and save.
`FUN_00503010` is a dword field and `FUN_00503070` is a byte field. In the current
format (`0x80000000` marker), the file order is:

| File offset | Profile offset | Type | Field |
| --- | --- | --- | --- |
| `0x00` | - | dword | format marker `0x80000000` |
| `0x04` | `+0x48` | dword | money |
| `0x08` | `+0x1C` | dword | tank (1-5) |
| `0x0C` | `+0x20` | dword | level (1-6; 6 = tank-complete sentinel) |
| `0x10` | `+0x59` | byte | Bonus Adventure flag |
| `0x11` | `+0x58` | byte | set by `FUN_00501370`; reader unknown |
| `0x12` | `+0x90` | dword | unknown |
| `0x16` | `+0x94` | dword | unknown |
| `0x1A` | `+0x8C` | dword | unknown |
| `0x1E` | `+0x4C` | dword | unknown |
| `0x22` | `+0x50` | dword | tank-5 completion counter (exact semantics Q-0015) |
| `0x26` | `+0x54` | dword | unknown |
| `0x2A` | `+0xA0` | dword | unknown |
| `0x2E` | `+0x98` | dword | unknown; reset assigns a generated value |
| `0x32` | `+0xB0` | dword | bonus-pet/upgrade card index 1-6 |
| `0x36` | `+0xB4` | dword | reset 3; Sandbox raises to 11; still open (Q-0013) |
| `0x3A..0x51` | `+0x00..+0x17` | 24 bytes | owned-pet flags |
| `0x52..0x57` | `+0x72..+0x77` | 6 bytes | six-byte block; reset writes only byte 0 = 1. Not proven to be the selected-pet array. |
| `0x58..0x5F` | `+0xA8..+0xAF` | 8 bytes | unknown |
| `0x60..0x83` | `+0x78..+0x7B`, `+0x11C..+0x128`, `+0x10C..+0x118` | 4 x (byte + 2 dwords) | four records, likely Challenge records; not proven |
| `0x84` | `+0x7C` | dword | candidate 32-bit story mask; reader not located |
| `0x88` | `+0x80` | dword | candidate gold-trophy/33rd-story flag; reader not located |
| `0x8C` | `+0x84` | dword | bitmask written by `FUN_005014D0`; load clears bit 6 |
| `0x90..0xE3` | `+0xB8..+0x10B` | 21 dwords | unknown; save/reset initializes them to `-1` |
| `0xE4` | `+0x88` | dword | trailing dword; not a plain CRC32 |

Total `0xE8` = 232 bytes, matching both samples.

### 3.1 Serializer details

- The 24 owned-pet bytes are `profile+0x00..+0x17`; `FUN_00501410(i)` reads one,
  `FUN_00501420(i,v)` writes one and adjusts the in-memory owned count `+0x18`.
- The 4 records are written as:
  `byte +0x78+i`, `dword +0x11C+4i`, `dword +0x10C+4i`.
- For the current format, `+0x7C`, `+0x80`, and `+0x84` follow the four records.
- The 21-dword block is `+0xB8..+0x10B`.
- The trailing `+0x88` is read/written only when the marker is greater than
  `0x7fffffff`; it is not a checksum verified by the code observed so far. A CRC32
  of the body did **not** match it.
- Legacy branch: when the loaded marker is `< 0x7fffffff`, `FUN_00503730` reads each
  record byte as a 4-byte boolean and skips `+0x7C/+0x80/+0x84`. Do not treat every
  historical file as the current 232-byte layout without checking the marker.

The GameBanana profile is maxed for money, pet flags, and the candidate story/trophy
fields. It has only three of the four record bytes set, so the upload's "100%" label
is not independently verified.

## 5. Trophy/story lead (Q-0013)

`+0x7C = 0xFFFFFFFF` and `+0x80 = 1` in the 100% profile is a strong numerical match
for a **32-bit story mask plus a 33rd gold-trophy flag**, and `FUN_00501530` clears
both fields next to the four record bytes. However:

- no instruction-level reader/writer for `+0x7C` or `+0x80` has been located;
- `+0xB4`/`+0xB0` from the original Q-0013 were not re-bound by this sample;
- the four record bytes are `1,1,1,0`, so the sample is not a clean four-tank
  Challenge completion.

Q-0013 therefore stays **OPEN**. The candidate labels are recorded as a lead only,
not as a proven trophy trigger.

## 6. Tank saves (`adv%d.dat`, `sim%d.dat`)

- `FUN_00546990` writes dword version `0x36`, calls `FUN_00546240` for the tank
  body, then writes a `__time64` value.
- `FUN_00546240` writes tank `+0x3C8` and level `+0x3CC` first.
- Early `adv1.dat`: 1081 bytes, version 54, tank/level `1,1`; contains the tank-1
  tutorial string at `0x184`.
- GameBanana `sim1.dat`: 11800 bytes, version 54, tank/level `1,5`. It is in the
  same save family; the `sim` prefix and the level-5 value are not yet bound.
- No `adv1.dat` or `scr1.dat` exists in the GameBanana pack.

## Implementation Plan for P4

1. **Model the profile with named fields, not raw offsets.** Create a
   `ProfileData` resource with `money`, `tank`, `level`, `bonus_adventure`, the 24
   owned-pet booleans, the 6-byte block, the 8-byte block, four record structs
   (`flag: bool`, `value_a: int`, `value_b: int`), the 21-dword block, and the
   candidate `story_mask` / `gold_trophy` fields. Keep unresolved fields as
   explicitly named `unknown_XX` values so future evidence can rename them without
   changing the save contract.
2. **Implement the writer in the exact serializer order.** Use the current marker
   path (`0x80000000`): money, tank, level, two bytes, ten dwords, 24 pet bytes,
   six bytes, eight bytes, four records, `+0x7C/+0x80/+0x84`, 21 dwords, trailing
   dword. Reproduce the legacy read branch only if compatibility with pre-current
   saves is required.
3. **Do not implement a checksum yet.** The trailing `+0x88` is not a verified
   CRC32; preserve it on load and write a documented placeholder or omit it until
   the real algorithm is proven. Prefer the remake's own versioned save format
   (P4.12) rather than promising byte compatibility.
4. **Separate profile data from tank data.** `user%d.dat` is the profile; `adv%d.dat`
   / `sim%d.dat` are tank saves with their own `0x36` body. Do not serialize tank
   entities into the profile record.
5. **Implement `users.dat` as a profile list.** Parse the `0x0E` version, uint16
   count, uint16 name length, name bytes, then the two trailing dwords. Preserve
   unknown trailing values when round-tripping. Resolve the active profile through
   the same `CurUser` mechanism.
6. **Keep the story/trophy gate data-driven.** Store the candidate 32-bit mask and
   gold flag, but do not hard-code a "100% = 0xFFFFFFFF" trigger until Q-0013 has a
   code-level reader. The remake can expose the mask in a debug view and gate story
   entries on bits only after the original mapping is confirmed.
7. **Add golden-file tests.** Round-trip the two provided `user1.dat` samples and
   compare every field; assert the 232-byte length and the observed offsets. Add a
   load test for a legacy marker to prove the branch is not silently used for
   current saves.
8. **Document the compatibility boundary.** If P4 uses its own format, state that
   it preserves profile semantics but not original bytes. If compatibility is
   required, add a separate importer/exporter and never overwrite the original
   `ProgramData` files.
