# P2.13 - Save/profile formats (partial)

Status: **in progress** (2026-10-29). Location, `users.dat`, the full
`user%d.dat` field order, the tank-save file naming (one file per game mode) and the
`scr%d.dat` escrow layout are documented. Tank-save field semantics and the
trophy/story binding remain open.

Primary evidence: EV-0108 (early local sample), EV-0109 (GameBanana sample +
`user%d.dat` serializer map), EV-0142 (tank-save name builder and the per-mode
files), EV-0143 (`scr%d.dat` layout and the Shells cash-in). Samples live under
`docs/analysis/inputs/p2.13-saves-2026-10-21/` and
`docs/analysis/inputs/p2.13-saves-gamebanana-100/`.

## 1. Locations and file roles

- Live user data: `C:\ProgramData\Steam\Insaniquarium\userdata` (not the game
  install folder).
- `users.dat` - profile list. Serializer `FUN_00513850`; list load/save
  `FUN_00514C00` / `FUN_00514D50`.
- `user%d.dat` - one profile slot. Load `FUN_005145A0`, save `FUN_00514730`,
  shared field serializer `FUN_00503730`.
- `adv%d.dat` / `tim%d.dat` / `snd%d.dat` / `sur%d.dat` / `sim%d.dat` - one
  tank save **per game mode** (EV-0142). The single builder
  `FUN_00505880(out, mode, slot)` formats `userdata\%s%d.dat` with the mode's
  prefix and the profile slot `[profile+0x44]`. Writer `FUN_00546990` (called
  from `FUN_005497A0`), tank serializer `FUN_00546240`; loader `FUN_00546AA0`
  (called from `FUN_0054CB20`); version dword `0x36`.
- `scr%d.dat` - bonus-shells **escrow**, not a tank save: 102 raw dwords whose first dword is the
  `profile+0x88` token and whose payload is the pending bonus-round Shells (`Tank+0x400`). Writer
  `FUN_00515910`, reader `FUN_005148C0`, cash-in `FUN_00514B00`; format in §7 (EV-0143).
  `FUN_005059D0` deletes it together with `user%d.dat` and the six mode files when a profile is
  removed (EV-0142).
- `highscores.dat` - string present in the module; format not parsed.

## 2. `users.dat`

Observed layouts:

| Sample | Bytes | Layout |
| --- | --- | --- |
| early local | 22 | `0E 00 00 00` \| `01 00` \| `06 00` \| `okokok` \| `01 00 00 00` \| `01 00 00 00` |
| GameBanana | 21 | `0E 00 00 00` \| `01 00` \| `05 00` \| `Roman` \| `04 00 00 00` \| `01 00 00 00` |

- `0x00` dword = `0x0E`; `FUN_00513850` compares it with `DAT_005e042c`, so it is
  a version/format value, not a count.
- `0x04` uint16 = profile count (1 in both samples).
- `0x06` uint16 = name length; the name follows as raw bytes.
- Two trailing dwords follow the name. They are `1,1` in the early sample and
  `4,1` in the GameBanana sample. Their meaning is **unresolved**; do not label
  the first one as a constant user ID.

The registry value `HKCU\Software\PopCap\Insaniquarium\CurUser` selects the active
profile name. The early sample stores `okokok` (6 characters), not `okokokok`.

## 3. `user%d.dat` - 232-byte profile slot

`FUN_00503730` is the single field serializer used by both load and save.
`FUN_00503010` is a dword field and `FUN_00503070` is a byte field. In the current
format (`0x80000000` marker), the file order is:

The offsets below are relative to the start of the 232-byte record. The enclosing
profile object also carries a runtime field at `+0x44` - the save-slot number that
appears in the `user`/`scr`/mode file names (EV-0142) - which is **not** part of the
record.

| File offset | Profile offset | Type | Field |
| --- | --- | --- | --- |
| `0x00` | - | dword | format marker `0x80000000` |
| `0x04` | `+0x48` | dword | money |
| `0x08` | `+0x1C` | dword | tank (1-5) |
| `0x0C` | `+0x20` | dword | level (1-6; 6 = tank-complete sentinel) |
| `0x10` | `+0x59` | byte | Bonus Adventure flag |
| `0x11` | `+0x58` | byte | set by `FUN_00501370`; reader unknown |
| `0x12` | `+0x90` | dword | unknown |
| `0x16` | `+0x94` | dword | unknown |
| `0x1A` | `+0x8C` | dword | unknown |
| `0x1E` | `+0x4C` | dword | unknown |
| `0x22` | `+0x50` | dword | tank-5 completion counter (exact semantics Q-0015) |
| `0x26` | `+0x54` | dword | unknown |
| `0x2A` | `+0xA0` | dword | unknown |
| `0x2E` | `+0x98` | dword | unknown; reset assigns a generated value |
| `0x32` | `+0xB0` | dword | bonus-pet/upgrade card index 1-6 |
| `0x36` | `+0xB4` | dword | reset 3; Sandbox raises to 11; still open (Q-0013) |
| `0x3A..0x51` | `+0x00..+0x17` | 24 bytes | owned-pet flags |
| `0x52..0x57` | `+0x72..+0x77` | 6 bytes | **backdrop ownership**, one flag per backdrop 0..5; reset writes only byte 0 = 1 (the default backdrop). The store sells a random unowned one for 15000 (EV-0141). |
| `0x58..0x5F` | `+0xA8..+0xAF` | 8 bytes | unknown |
| `0x60..0x83` | `+0x78..+0x7B`, `+0x11C..+0x128`, `+0x10C..+0x118` | 4 x (byte + 2 dwords) | four records, likely Challenge records; not proven |
| `0x84` | `+0x7C` | dword | candidate 32-bit story mask; reader not located |
| `0x88` | `+0x80` | dword | candidate gold-trophy/33rd-story flag; reader not located |
| `0x8C` | `+0x84` | dword | bitmask written by `FUN_005014D0`; load clears bit 6 |
| `0x90..0xE3` | `+0xB8..+0x10B` | 21 dwords | unknown; save/reset initializes them to `-1` |
| `0xE4` | `+0x88` | dword | trailing dword; not a plain CRC32 |

Total `0xE8` = 232 bytes, matching both samples.

### 3.1 Serializer details

- The 24 owned-pet bytes are `profile+0x00..+0x17`; `FUN_00501410(i)` reads one,
  `FUN_00501420(i,v)` writes one and adjusts the in-memory owned count `+0x18`.
- The 4 records are written as:
  `byte +0x78+i`, `dword +0x11C+4i`, `dword +0x10C+4i`.
- For the current format, `+0x7C`, `+0x80`, and `+0x84` follow the four records.
- The 21-dword block is `+0xB8..+0x10B`.
- The trailing `+0x88` is read/written only when the marker is greater than
  `0x7fffffff`; it is not a checksum verified by the code observed so far. A CRC32
  of the body did **not** match it.
- Legacy branch: when the loaded marker is `< 0x7fffffff`, `FUN_00503730` reads each
  record byte as a 4-byte boolean and skips `+0x7C/+0x80/+0x84`. Do not treat every
  historical file as the current 232-byte layout without checking the marker.

## 5. Trophy/story lead (Q-0013)

`+0x7C = 0xFFFFFFFF` and `+0x80 = 1` in the 100% profile is a strong numerical match
for a **32-bit story mask plus a 33rd gold-trophy flag**, and `FUN_00501530` clears
both fields next to the four record bytes. However:

- no instruction-level reader/writer for `+0x7C` or `+0x80` has been located;
- `+0xB4`/`+0xB0` from the original Q-0013 were not re-bound by this sample;
- the four record bytes are `1,1,1,0`, so the sample is not a clean four-tank
  Challenge completion.

Q-0013 therefore stays **OPEN**. The candidate labels are recorded as a lead only,
not as a proven trophy trigger.

## 6. Tank saves - one file per game mode (`adv`/`tim`/`snd`/`sur`/`sim`)

`FUN_00505880(out, mode, slot)` is the only builder of tank-save names: it picks a
three-letter prefix from the game mode, then formats `userdata\%s%d.dat`
(`FUN_004120C0`, format string at 0x59D5E4) with `slot = [profile+0x44]` and
returns the result in a `std::string` (EV-0142).

| `mode` = `[manager+0x87C]` | Prefix | String | File |
| --- | --- | --- | --- |
| 0 Adventure (also mode 2, unobserved) | `adv` | 0x59D5F8 | `userdata\adv<N>.dat` |
| 1 Time Trial | `tim` | 0x59D604 | `userdata\tim<N>.dat` |
| 3 Sandbox | `snd` | 0x59D5FC | `userdata\snd<N>.dat` |
| 4 Challenge | `sur` | 0x59D600 | `userdata\sur<N>.dat` |
| 5 Virtual Tank | `sim` | 0x59D608 | `userdata\sim<N>.dat` |

- Save chain: `FUN_005497A0` (path from the builder) -> if `FUN_00537BF0()` is
  false it deletes the file (`FUN_0047FBC0`), else `FUN_00411BC0("userdata")`
  (create directory) and `FUN_00546990(path)` = SaveGame. `FUN_00546990` writes
  dword version `0x36`, calls `FUN_00546240` for the tank body, then writes a
  `__time64` value.
- Load chain: `FUN_0054CB20` -> path -> `FUN_00546AA0(path)` = LoadGame; a failed
  load falls through to a fresh tank (`FUN_0054BC30`).
- `FUN_00546240` writes tank `+0x3C8` and level `+0x3CC` first.
- `FUN_0047FBC0` is a `DeleteFileA` wrapper gated by `[app+0x511]`. The
  delete-all routine for a profile is `FUN_005059D0`: `userdata/user<N>.dat`,
  `userdata/scr<N>.dat`, then `i = 0..5` through the builder - so every mode's
  file is removed.
- Early `adv1.dat`: 1081 bytes, version 54, tank/level `1,1` (mode 0 / slot 1);
  contains the tank-1 tutorial string at `0x184`.
- GameBanana `sim1.dat`: 11800 bytes, version 54, tank/level `1,5` (mode 5 /
  slot 1). Same version and body family; the size gap is content (a populated
  Virtual Tank), not a second format. The level-5 value is not yet explained.
- No `adv1.dat` or `scr1.dat` exists in the GameBanana pack.

## 7. `scr%d.dat` - the bonus-shells escrow (EV-0143)

`FUN_00515910` (write) and `FUN_005148C0` (read) are the whole of this file; nothing else opens it.

- **Purpose.** `Tank+0x400` collects the shells of a bonus round (EV-0073) and is **not** part of the
  tank save. `FUN_00546990` (SaveGame) flushes it after the tank file is written -
  `if (thunk_FUN_00479FC0()) { FUN_00515910(Tank+0x400); Tank+0x400 = 0; }` - so the escrow carries
  bonus shells across a save/load cycle.
- **Cash-in.** `FUN_00514B00` (profile method): `v = FUN_005148C0(1)` (read + delete), clamp
  `v > 100000 -> 100000`, return when `v <= 0`, else `FUN_00501200(v)` (add to Shells,
  `profile+0x48`), `profile+0x88 = FUN_0040F9E0()` (fresh random token), then `FUN_00514730`
  (profile save). Four call sites: `FUN_00546AA0` (tank load, demo branch), `FUN_0054BCA0`
  (pre-bonus store screen), `FUN_0054BF60` (BonusScreen opener) and `FUN_00552100` (session setup,
  gated on a live profile at `manager+0x8B8`).
- **Format** - 102 little-endian dwords = `0x198` bytes, no header, no cipher, no checksum:

| Offset | Content |
| --- | --- |
| `0x000` | **token** - must equal `profile+0x88`, the random dword that `user%d.dat` keeps as its trailing field |
| `0x004..0x0C7` | 50 filler dwords, each `rand() % 20000` |
| `0x0CC` | **payload** - the escrowed shell amount |
| `0x0D0..0x197` | 50 filler dwords, each `rand() % 20000` |

- **The token is the anti-tamper.** A mismatch returns 0 *and* deletes the file, so a `scr%d.dat`
  copied onto another slot - or a `user%d.dat` edited so the trailing dword no longer matches - loses
  the escrow instead of paying it out. The filler is never validated; it only makes hand-editing
  harder.
- **Stream plumbing.** `FUN_0047F5D0(path, outString, 0)` reads the whole file into a `std::string`
  (raw `ReadFile` loop in the real-file branch, returns 1/0); `FUN_005001D0` + `FUN_00502FC0(data,
  size, 0)` build the `Buffer`, `FUN_00500340`/`FUN_005004E0` are the raw 4-byte read/write,
  `FUN_00502FB0`/`FUN_005030E0` release it. There is no format header to skip: the only structured
  reader in this family, `FUN_00513E30`, is a `Sexy::DataSync` constructor and the escrow writer
  never calls it.
- Neither sample pack holds a `scr%d.dat`, consistent with "no bonus shells pending".

## 8. Open items

- Q-0015: `profile+0x58` reader; exact `+0x50` meaning.
- Q-0019: **settled** by EV-0143 - format, return path and cash-in are documented in §7. The only
  residue is the intent of the two `thunk_FUN_00479FC0()` (demo/registered) branches: the full
  version banks `Tank+0x400` at save, the demo cashes the escrow at load, and why they differ is not
  visible in the code.
- The save/resume gate `FUN_00537BF0()` (save when true, delete when false), the
  `[app+0x511]` no-write flag, and the level-5 value in `sim1.dat`.
- `users.dat` trailing dwords.
- `user%d.dat` meanings of `+0x90`, `+0x94`, `+0x8C`, `+0x4C`, `+0x54`, `+0xA0`,
  `+0x98`, `+0xB4`, the 8-byte block, the four records, the 21-dword block, and
  `+0x88`.
- `profile+0x44` (outside the serialized range) is the save-slot number used by
  all three file families; what writes it is not located.

## Implementation Plan for P4

1. **Model the profile with named fields, not raw offsets.** Create a
   `ProfileData` resource with `money`, `tank`, `level`, `bonus_adventure`, the 24
   owned-pet booleans, the 6-byte block, the 8-byte block, four record structs
   (`flag: bool`, `value_a: int`, `value_b: int`), the 21-dword block, and the
   candidate `story_mask` / `gold_trophy` fields. Keep unresolved fields as
   explicitly named `unknown_XX` values so future evidence can rename them without
   changing the save contract.
2. **Implement the writer in the exact serializer order.** Use the current marker
   path (`0x80000000`): money, tank, level, two bytes, ten dwords, 24 pet bytes,
   six bytes, eight bytes, four records, `+0x7C/+0x80/+0x84`, 21 dwords, trailing
   dword. Reproduce the legacy read branch only if compatibility with pre-current
   saves is required.
3. **Do not implement a checksum yet.** The trailing `+0x88` is not a verified
   CRC32; preserve it on load and write a documented placeholder or omit it until
   the real algorithm is proven. Prefer the remake's own versioned save format
   (P4.12) rather than promising byte compatibility.
4. **Separate profile data from tank data.** `user%d.dat` is the profile; the
   tank saves are one file **per game mode** (`adv`/`tim`/`snd`/`sur`/`sim` + the
   profile slot, EV-0142), each with its own `0x36` body. Do not serialize tank
   entities into the profile record, and keep one tank slot per mode.
5. **Implement `users.dat` as a profile list.** Parse the `0x0E` version, uint16
   count, uint16 name length, name bytes, then the two trailing dwords. Preserve
   unknown trailing values when round-tripping. Resolve the active profile through
   the same `CurUser` mechanism.
6. **Keep the story/trophy gate data-driven.** Store the candidate 32-bit mask and
   gold flag, but do not hard-code a "100% = 0xFFFFFFFF" trigger until Q-0013 has a
   code-level reader. The remake can expose the mask in a debug view and gate story
   entries on bits only after the original mapping is confirmed.
7. **Add golden-file tests.** Round-trip the two provided `user1.dat` samples and
   compare every field; assert the 232-byte length and the observed offsets. Add a
   load test for a legacy marker to prove the branch is not silently used for
   current saves.
8. **Document the compatibility boundary.** If P4 uses its own format, state that
   it preserves profile semantics but not original bytes. If compatibility is
   required, add a separate importer/exporter and never overwrite the original
   `ProgramData` files.
9. **Carry the bonus-shell escrow, not the file.** The original exists because `Tank+0x400` (bonus
   shells) is absent from the tank body: a save banks it in `scr%d.dat`, and the next bonus-related
   screen or tank load pays it back into `profile+0x48`. In the remake, keep the counter in the tank
   save or in the profile and pay it exactly once - the failure mode to avoid is losing shells when a
   player quits mid-bonus **or** paying them twice. Do not model the token/filler: they only exist to
   reject hand-edited files.
